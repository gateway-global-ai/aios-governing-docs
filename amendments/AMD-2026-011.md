# AMD-2026-011 — External Repository Acquisition, Quarantine, Promotion, and Minimal Governance Execution Dependencies

## 0. Identifier note

**Council / editors:** The topic described in the architecture brief as “AMD-2026-009” for this package **cannot** use document id **AMD-2026-009** in this repository — **AMD-2026-009** is already allocated to *Intent-Scoped Web Retrieval and Governed Website Review*. This amendment is **AMD-2026-011**. **AIOS-SPEC-009** remains reserved for the *Intent Primitive and Execution Model*. Normative **contracts** and **promotion classes** for acquisition are drafted as **[AIOS-SPEC-013](../specifications/ExternalRepositoryAcquisitionAnalysisAndPromotion.md)** (this amendment’s follow-on).

---

## 1. Rationale

### 1.1 Scope boundaries

This amendment **governs**:

- **Ingestion of external *repositories*** (source trees, not single-page web retrieval — that remains **AMD-2026-009**).
- **Policy and CI discipline** for *this* governing-documents repository’s integrity automation.

This amendment **does not**:

- Mandate a particular acquisition **storage backend** or vendor CI product.
- Replace **AIOS-SPEC-003** intent emission rules; it **aligns** acquisition with them.
- Treat **governance markdown authoring**, **runtime MCP**, and **design-time acquisition tooling** as the same plane — see **AIOS-SPEC-013** §11.

External repositories contain code, configuration, and dependency surfaces that can affect **security**, **reproducibility**, **ingestion trust boundaries**, and **CI discipline**. Treating acquisition as an unstructured, operator-local activity breaks alignment with governed intent, audit, and promotion models already established for documents and Workspace integration.

This amendment establishes **normative principles** for how external repositories enter the AI OS ecosystem: **acquisition intent**, mandatory **quarantine**, structured **analysis**, **promotion** only after governance requirements are met, and **ratification** or tier-appropriate approval for system-wide reuse. It also adopts the **minimal execution dependency principle** for governance and CI automation so integrity checks depend only on packages required at execution time — not the full LLM/MCP stack used by optional pipeline scripts.

## 2. Normative principles

### 2.1 Terminology (distinct concerns)

| Term | Meaning in this amendment |
|------|---------------------------|
| **Acquisition intent** | Declared, attributable request to obtain an external repository for governed processing — see **AIOS-SPEC-013** §1. |
| **Quarantine** | Mandatory initial isolation state before operational binding; see §2.2.3 and **AIOS-SPEC-013** §2. |
| **Analysis** | Structured review (license, dependencies, secrets surface, APIs, risk class) before promotion; see §2.4 and **AIOS-SPEC-013** §§3–7. |
| **Promotion** | Governed transition toward **approved** or **vendored / reusable** classes; see §2.4 and **AIOS-SPEC-013** §8. |
| **Minimal execution dependency principle** | CI and scripts install **only** packages required for the invoked check; see §2.5. |

### 2.2 Acquisition path

1. **No standing manual acquisition.** External repositories **must not** be cloned or copied into governed or production runtime repositories by individuals as a **normal** or **standing** workflow. **Acquisition intent** **must** be emitted through **governed channels** (automated jobs or operator actions that **record** intent and audit metadata). One-off exploratory clones **outside** governed trees may occur under local policy, but **must not** satisfy acquisition for operational or system-wide reuse — reuse **requires** intent, quarantine, analysis, and promotion per this amendment and **AIOS-SPEC-013**. Copying, importing, or otherwise moving external repository artifacts into governed or production trees without a recorded acquisition intent is **prohibited** and does **not** substitute for the governed acquisition path.

2. **Intent-driven acquisition.** **Acquisition intent** is the binding declaration that a specific external source is to be obtained for evaluation. It **must** be recordable, attributable, and consistent with applicable policy (scope class, tenant, and audit expectations).

3. **Quarantine by default.** Every acquired external repository **must** begin in **quarantine**: isolated from operational deployment paths, production promotion, and system-wide reuse until required **analysis** steps complete.

### 2.3 Machine-readable repository specification

For each acquired repository, the system **must** extract and preserve a **machine-readable** record (single document or structured bundle) that includes, at minimum:

| Field | Description |
|-------|-------------|
| **Source URL** | Canonical clone/fetch location. |
| **Branch / commit** | When known — pinned revision preferred for reproducibility. |
| **Authoritative documentation URLs** | Official docs, security advisories, license references. |
| **Runtime dependencies** | Dependency manifests as applicable (e.g. lockfiles, package lists). |
| **Required environment variables / secrets** | Names and purpose; not secret values. |
| **External APIs / services** | Identifiers and purpose. |
| **Capability classification** | Alignment with platform capability taxonomy (e.g. read-only tool, data plane, network egress). |
| **Execution / risk class** | Sandboxing, data sensitivity, and blast-radius tier. |

Updates to this record **must** be versioned or timestamped when acquisition state changes.

### 2.4 Analysis, promotion, and ratification

4. **No operational use before governance.** An acquired repository **must not** be used **operationally** (runtime default, shared library for production, or system-wide automation) until it completes **analysis** (security, license compatibility, dependency and secret review per policy) and passes the **promotion** path defined for its risk class.

5. **Promotion** is the governed transition from **quarantine** toward **approved reuse** within defined boundaries (scope, environment, and version pins); it **may** include intermediate states (**evaluation**, **sandbox**, etc.) as defined in **AIOS-SPEC-013** §8 where applicable. **System-wide** or **normative** reuse may require **ratification** artifacts or Council-equivalent approval per **AIOS-CORE-002** and **AIOS-SPEC-003** peer-review and ratification rules.

6. **Sandboxing** where policy requires it remains mandatory before promotion for high-risk execution classes.

### 2.5 Minimal execution dependency principle (governance / CI)

7. **Minimal install surface.** Governance and CI jobs **must** declare and install **only** the dependencies required to execute the specific check or script invoked. Broad package stacks (LLM SDKs, application servers, test frameworks) **must not** be installed when unused by that job.

8. **Repository alignment.** This repository’s **Governance integrity** workflow uses [`scripts/requirements.governance-integrity.txt`](../scripts/requirements.governance-integrity.txt) for `scripts/governance_integrity_check.py` — a **concrete** application of this principle. Full pipeline tooling continues to use [`scripts/requirements.txt`](../scripts/requirements.txt). Optional scripts **must not** be implied as required for integrity unless a governed change says otherwise.
