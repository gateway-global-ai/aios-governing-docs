# AMD-2026-010 — Kernel Engineer Role and Specialist Kernel Review Lane (Shadow Pilot)

## 0. Status

| Field | Value |
|-------|--------|
| **Status** | `ratified` — **v0.2.0** (`ratification_target` **2026-04-08**) |
| **Ratification** | **[AMD-2026-010-RATIFICATION-MOTION](AMD-2026-010-ratification-motion.md)** v1.0.0 **approved** **2026-04-08**; peer review **[reviews/amd_2026_010/round_2/](../reviews/amd_2026_010/round_2/)** |

This amendment **does not** replace the **triangulated peer review consortium** or the **current ratification path**. It **introduces** a **specialist kernel review lane** to run in **shadow mode** (parallel, non-blocking) until evaluation justifies a later adoption decision.

---

## 1. Purpose

Governed AI OS implementations depend on **correctness of the shell and control plane**: shell state, authority boundaries, routing invariants, session-node integrity, voice/UI parity, **shell-state vs skill** separation, **primary vs operator** integrity, and **truthful disclosure** of state. These concerns are **not ordinary feature work**; when diffused across **general** reviewers alone, defects can pass as “acceptable editorial” or “minor technical” feedback while **violating architecture**.

This amendment **formalizes**:

1. A **Kernel Engineer** role — explicit ownership and review focus for kernel-adjacent integrity.
2. A **Kernel review lane** — specialist review scope aligned with that role.
3. A **shadow-mode pilot** — run **alongside** the existing triangulated committee; **not** a replacement **yet**; **not** automatically blocking **yet**.

**Non-goals (this amendment)**

- Rewriting the entire review system or superseding **[AMD-2026-005](../amendments/AMD-2026-005.md)** lifecycle thresholds.
- Changing **AMD-2026-005** composite or per-dimension **thresholds** as a side effect of this text; any threshold change **SHALL** be a **follow-on amendment** if ever required.
- Mandating runtime implementation details in product repositories (those remain separate change control).

---

## 2. Scope

**In scope**

- Definitions and responsibilities for the **Kernel Engineer** role (governance / product architecture).
- Definition of the **Kernel review lane** and its **focus areas**.
- **Shadow rollout** rules: parallel operation with the **existing** triangulated review process; **non-blocking** by default during the pilot.
- **Evaluation criteria** for the pilot (whether to adopt, merge, or retire the lane).

**Out of scope**

- Abolishing or replacing the **current** OpenAI / Gemini / DeepSeek (or successor) **triangulated** committee as the **active** ratification path **at this time**.
- Automatic **blocking** gate on merge or ratification solely from kernel review **until** a future amendment or Council decision says otherwise.
- Full **identity/RBAC** specification for who may hold the Kernel Engineer role in every organization (operational assignment remains with each program).

## 3. Definitions

| Term | Definition |
|------|------------|
| **Kernel** (informative, in this amendment) | The **shell control plane** and **system-state** concerns that **must** stay coherent with **[AMD-2026-007](../amendments/AMD-2026-007.md)** (shell vs skills, primary vs operator, disclosure) and normative specs (**AIOS-SPEC-006**, **AIOS-SPEC-009**, etc.) — **not** the Linux kernel. |
| **Kernel Engineer** | A **designated** governance/product-architecture role responsible for **kernel integrity** (Section 4.1). Distinct from **Domain/Pack Engineer**, **Capability/Adapter Engineer**, and **ordinary feature implementation**. |
| **Domain/Pack Engineer** (contrast) | Owns **domain packs**, capability registries, and **Workspace**-shaped **fulfillment** — **not** the shell control plane’s **classification** of shell vs skill vs governance intent. |
| **Capability/Adapter Engineer** (contrast) | Owns **adapters**, MCP/control-plane **transport**, and **scope** mapping — **not** shell **routing invariants** or **UI parity** of shell affordances. |
| **Kernel review lane** | A **specialist** review pass (human and/or assisted) whose **rubric** emphasizes shell/state/authority/routing parity (Section 4.2). |
| **Shadow mode** | Kernel review **runs in parallel** with the **existing** triangulated review; outcomes are **recorded** and **used for learning**; they **do not** by themselves **block** ratification during the pilot. |
| **Triangulated committee** | The **existing** peer-review consortium and lifecycle described in **[reviews/README.md](../reviews/README.md)** and **[AMD-2026-005](../amendments/AMD-2026-005.md)** — remains the **authoritative** path for **draft → review → thresholds → ratification** unless and until a future amendment changes that. |

## 4. Normative decisions

**Binding vs advisory (this section).** **SHALL NOT** in Section 4.3 is **normative** for the shadow pilot: the kernel lane **must not** replace Round 1 / Round 2 triangulation **during** the pilot. **SHOULD** in Sections 4.1–4.2 describes **recommended** program practice and lane scope **without** imposing obligations beyond each program’s own governance (e.g. naming a Kernel Engineer). Rubric annexes under Section 4.3 **must not** invalidate **[AMD-2026-005](../amendments/AMD-2026-005.md)** thresholds unless a **future** amendment updates them. **Section 4.4** is **normative** for the **legal/process** status of **pilot-phase** kernel outputs (advisory and non-binding for ratification gates).

### 4.1 Kernel Engineer role

**The program SHOULD designate at least one Kernel Engineer** (or a named delegate with the same charter) for each major AI OS release line or governed product family.

**The Kernel Engineer is responsible for** (non-exhaustive):

1. **Shell control plane integrity** — command rail, shell affordances, and **shell-state** transitions remain **first-class** and **not** conflated with **skills**, **tools**, or **domain execution** (see **[AMD-2026-007](../amendments/AMD-2026-007.md)** §11.9, **POL-SHELL-***).
2. **System-state invariants** — what **may** be true concurrently (e.g. session summaries, canvas vs shell) without contradiction.
3. **Authority and disclosure boundaries** — operator vs primary presentation; **truthful** “where am I / what is blocked?” disclosure.
4. **Command rail / shell semantics** — voice ↔ chat parity where required by policy; **no silent** misrouting of shell intent.
5. **Action classification at runtime** — **shell-state** vs **governance intent** vs **workspace capability** vs **local lane** — alignment with **AIOS-SPEC-009** and **AIOS-SPEC-006** registry discipline.
6. **Prevention of shell-state / skill-layer drift** — catching refactors that **smuggle** domain logic into shell or **weaken** invariants.

**The Kernel Engineer is not** a substitute for **legal**, **compliance editorial**, or **full-stack feature** ownership; **coordination** with those lanes **SHALL** be explicit.

### 4.2 Kernel review lane

**The Kernel review lane SHOULD** evaluate change sets (PRs, amendment drafts, spec deltas) for:

| Focus | Examples |
|-------|----------|
| **Shell invariants** | Shell state not modeled as skills; POL-SHELL alignment. |
| **State / skill boundary** | No accidental coupling; intent primitive honored. |
| **Authority gating** | Operator/developer/primary rules consistent with policy and disclosure. |
| **Routing ambiguity** | Single resolution path for `app.*` / `governance.*` / `workspace.*` where normative. |
| **Voice/UI parity** | Required shell affordances per **[AMD-2026-007](../amendments/AMD-2026-007.md)** §4.1. |
| **Session truth** | Composed disclosure not misleading; identifiers in correct surface. |

**Outputs** SHOULD be **actionable** (pass / request changes with **specific** invariant references), not generic praise or blame.

### 4.3 Relationship to the triangulated committee

1. **Triangulated peer review** remains the **default ratification path** for governed documents under **[AMD-2026-005](../amendments/AMD-2026-005.md)**.
2. **Kernel review** in **shadow mode** **SHALL NOT** replace Round 1 / Round 2 **triangulation** **during the pilot**.
3. **Kernel review** **MAY** use the **same** or a **subset** rubric dimensions; **MAY** add **kernel-specific** checklist items **as an annex** to review packages — **without** invalidating **[AMD-2026-005](../amendments/AMD-2026-005.md)** thresholds unless a **future** amendment updates them.

### 4.4 Legal status of pilot findings (NORMATIVE)

During the **shadow pilot** phase defined in this amendment (Sections 5–6), **all** findings, recommendations, or reports produced by the **Kernel Engineer** or through the **Kernel review lane** are **strictly advisory and non-binding**. They **do not** constitute a formal **rejection**, a **required** change, or a **gating** condition for **ratification** or **merge** of governed documents under **[AMD-2026-005](../amendments/AMD-2026-005.md)**. The **triangulated peer review** disposition under that lifecycle remains the **sole** source of **binding** review outcomes for governed-document **ratification** **unless and until** a Council-approved **follow-on amendment** explicitly authorizes a **blocking** kernel gate. The purpose of kernel findings during the pilot is **data collection** and **process evaluation** as described in Section 6.

---

## 5. Recommended shadow rollout

1. **Parallel execution:** For selected documents or PRs, run **Kernel review** **after** or **alongside** assignment to the **standard** triangulated review queue — **not** instead of it.
2. **Non-blocking:** **Kernel review** outcomes are **informational** for **gate** purposes **until** Council or a ratified follow-on adopts blocking rules.
3. **Transparency:** Record kernel findings in the same **review archive** pattern (e.g. `reviews/<slug>/kernel/` or labeled sections in `REVIEW_SYNTHESIS.md`) so **overlap** and **unique yield** can be measured.
4. **Duration:** Pilot **at least** two **full** amendment or spec cycles **or** **six months**, whichever is longer, before proposing **merge** of kernel lane into **blocking** status.
5. **Exit criteria:** Proceed to a **follow-on amendment** only if evaluation (Section 6) shows **clear value**; otherwise **retire** or **merge** kernel checks into the **general** rubric **without** a separate lane.

## 6. Review / evaluation criteria (pilot)

| Criterion | Question |
|-----------|----------|
| **Baseline** | Establish a **baseline** before the pilot (e.g. last two cycles without kernel lane) so **unique yield** and **miss** rates are comparable. |
| **Unique issue yield** | Does kernel review surface issues **not** raised (or not raised with clarity) in triangulated technical/editorial/compliance lanes? |
| **Actionability** | Are findings tied to **specific** norms (**AMD-2026-007**, **POL-SHELL-***, SPEC sections)? |
| **Intelligibility** | Can **non-kernel** readers understand **why** something is a kernel defect vs a feature preference? |
| **Overlap** | What fraction of kernel findings **duplicate** triangulation vs **novel**? |
| **Miss detection** | Did any **shell/state/routing** incident **escape** both triangulation **and** kernel review? (post-mortem flag) |
| **Cost** | Time and reviewer load — acceptable vs **fatigue**? |

**Success (informative):** **Unique yield** ↑, **actionability** high, **overlap** manageable, **misses** ↓ vs baseline.

## 8. Implementation / process alignment

1. **Assignment:** Program lead **SHOULD** name Kernel Engineer(s) in **internal** runbooks; **MAY** publish in **DOCUMENT_REGISTRY** metadata **if** the registry schema is extended in a separate change.
2. **Review packages:** For drafts seeking ratification, **REVIEW_BRIEF** **MAY** include a **Kernel** subsection (questions, pointers to §11.9 / POL-SHELL).
3. **Product repos:** Runtime repos **SHOULD** link **shell-state** change logs to **policy IDs** where applicable; Kernel Engineer **reviews** those links in shadow mode.
4. **No AMD-2026-005 threshold change** is enacted by this amendment; **composite ≥ 3.5** and **no dimension below 3** remain as **[AMD-2026-005](../amendments/AMD-2026-005.md)** states **unless** a future amendment revises them.
